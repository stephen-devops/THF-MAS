================================================================================
MULTI-AGENT ARCHITECTURE ANALYSIS FOR THF (THREAT HUNTING FRAMEWORK)
================================================================================
Date: 2026-04-15
Scope: Evaluating supervisor/subagent architecture for the Wazuh Security Agent

================================================================================
1. CURRENT ARCHITECTURE SUMMARY
================================================================================

Single-agent design:
  - Model: claude-sonnet-4-20250514 (temperature=0.1, max_tokens=3000)
  - Agent type: Structured Chat Zero Shot React Description (LangChain)
  - 8 LangChain tools (WazuhBaseTool subclasses), each routing to 2-4 sub-functions:
      1. AnalyzeAlertsTool    -> rank, count, filter, distribution  (4 functions)
      2. InvestigateEntityTool -> alerts, details, activity, status (4 functions)
      3. MapRelationshipsTool  -> entity_to_entity, behavioral     (2 functions)
      4. DetectThreatsTool     -> technique, tactic, actor, IoCs, chains (5 functions)
      5. FindAnomaliesTool     -> threshold, behavioral, trend      (3 functions)
      6. TraceTimelineTool     -> sequence, progression, temporal   (3 functions)
      7. CheckVulnerabilitiesTool -> list_by_entity, cve, patches  (3 functions)
      8. MonitorAgentsTool     -> status, version, health           (3 functions)
  - Total: 8 tool schemas + ~27 underlying execute() functions across 44 Python files
  - ConversationSummaryBufferMemory for session-based context (1500 token limit)
  - ConversationContextProcessor for regex-based context enrichment
  - WazuhBaseTool._merge_context_filters() for contextual parameter inheritance
  - max_iterations=15 per agent executor run

Key observations from the codebase:
  - System prompt: ~55 lines, heavily focused on anomaly detection formatting rules
  - Tool descriptions are extremely verbose (MapRelationshipsTool alone is ~50 lines)
  - Every LLM call receives ALL 8 tool schemas regardless of query relevance
  - The example workflow (example_multi-request_workflow.txt) shows 3 sequential tool
    invocations for a single user query, with the agent adapting mid-investigation
    (retrying with full process path when short name fails)

================================================================================
2. PROPOSED MULTI-AGENT ARCHITECTURE
================================================================================

As described:
  - Supervisor Agent (wazuh_agent.py LLM): centralised control, conversation context
    management, tool routing decisions
  - 8 Subagents: one per tool, stateless, specialised prompts, cannot recall previous
    context, each wrapping a single WazuhBaseTool with its sub-functions
  - Supervisor decides synchronous or asynchronous invocation of subagents

================================================================================
3. BENEFITS OF THE MULTI-AGENT APPROACH
================================================================================

3.1 REDUCED PER-CALL TOKEN CONSUMPTION
  Currently, every LLM invocation sends all 8 tool schemas (~2000+ tokens of tool
  descriptions alone) plus the full system prompt. In the multi-agent model:
  - The supervisor's prompt contains only routing logic and short tool summaries
  - Each subagent receives only its own tool schema and a focused system prompt
  - Estimated 40-60% reduction in input tokens per subagent call

3.2 SPECIALISED SYSTEM PROMPTS PER TOOL
  The current system prompt tries to cover everything (anomaly formatting, threshold
  terminology, context preservation). With subagents:
  - The anomaly-specific formatting rules (lines 88-117 of wazuh_agent.py) only go
    to the FindAnomalies subagent
  - MapRelationships subagent gets its own prompt focused on entity direction logic
  - Each subagent prompt can include domain-specific few-shot examples
  - No risk of instructions for one tool polluting reasoning for another

3.3 INDEPENDENT MODEL SELECTION PER SUBAGENT
  Not all tools require the same reasoning capability. Potential model assignments:
  - Supervisor: claude-sonnet-4 (needs strong reasoning for routing and synthesis)
  - MonitorAgents subagent: Could use a cheaper/faster model (simple parameter extraction)
  - MapRelationships subagent: Needs stronger model (complex directional reasoning)
  - AnalyzeAlerts subagent: Could use cheaper model (straightforward parameter mapping)
  This could reduce cost by 20-40% while maintaining quality where it matters.

3.4 PARALLEL TOOL EXECUTION
  The supervisor could invoke multiple subagents concurrently for queries like:
  "Show me alert trends and check for anomalies on host X"
  - Currently: sequential (Thought -> Action -> Observation -> Thought -> Action -> ...)
  - Multi-agent: supervisor dispatches FindAnomalies + AnalyzeAlerts in parallel
  - Potential 40-50% latency reduction for multi-tool queries

3.5 EASIER TOOL ADDITION AND MAINTENANCE
  Adding a new tool (e.g., "CorrelateIntelligence") requires only:
  - A new subagent with its own prompt and schema
  - A short routing description added to the supervisor
  - No re-testing of existing subagent prompts
  - Current approach requires re-validating that new tool descriptions don't confuse
    the single agent's routing for existing tools

3.6 ISOLATED FAILURE HANDLING
  If a subagent fails or times out:
  - Supervisor can retry with different parameters or fall back gracefully
  - One subagent's failure doesn't corrupt the scratchpad for other tool calls
  - Currently, a parsing error mid-chain (as seen with "Invalid or incomplete response"
    in the workflow example) can derail the entire agent execution

================================================================================
4. DRAWBACKS AND RISKS
================================================================================

4.1 LATENCY MULTIPLICATION (HIGH IMPACT)
  Every tool invocation now requires:
    User -> Supervisor LLM call -> Subagent LLM call -> Supervisor LLM call -> User
  Minimum overhead per tool: +1 LLM round-trip (subagent call)
  For the 3-tool workflow in example_multi-request_workflow.txt:
    Current: 3 tool calls within 1 agent executor session (~4-6 LLM calls total)
    Multi-agent: 1 supervisor call + 3 subagent calls + 2 supervisor continuation calls
                 = ~6-8 LLM calls minimum
  With Anthropic API latency (~2-4s per call), this adds 4-8 seconds to complex queries.
  Mitigation: Parallel subagent execution where tools are independent.

4.2 LOSS OF ADAPTIVE MULTI-STEP REASONING (HIGH IMPACT)
  The example workflow demonstrates critical adaptive behaviour:
    Step 1: map_relationships with source_id="OneDrive.exe" -> 0 results
    Step 2: Agent independently decides to retry with full Windows path -> 0 results
    Step 3: Agent pivots to analyze_alerts with rule.id filter -> 18 results
  In the current architecture, the agent reasons about intermediate failures and adapts
  autonomously within a single execution session. With stateless subagents:
  - The MapRelationships subagent returns 0 results to the supervisor
  - The supervisor must understand WHY it failed (short name vs full path)
  - The supervisor must decide to retry with modified parameters
  - This requires the supervisor to have deep understanding of each tool's internals,
    partially defeating the purpose of specialisation
  This is the MOST SIGNIFICANT drawback. The current architecture's strength is its
  ability to chain tools with intermediate reasoning within a single context.

4.3 CONTEXT LOSS IN STATELESS SUBAGENTS (HIGH IMPACT)
  The current ConversationContextProcessor and _merge_context_filters() rely on:
  - Access to the agent's _current_context_result
  - Chat history for contextual reference detection
  - Previous tool call parameters extracted from conversation memory
  With stateless subagents:
  - Each subagent has no conversation history
  - The supervisor must extract ALL relevant context and pass it explicitly
  - Context enrichment (e.g., "these alerts" -> host=U209-PC-BLEE, time_range=3h)
    must happen entirely in the supervisor before delegation
  - Risk of context being lost or incorrectly transferred between layers

4.4 INCREASED API COST (MEDIUM IMPACT)
  Even with cheaper subagent models, total token consumption may increase:
  - Supervisor calls: routing logic + context serialisation + result synthesis
  - Subagent calls: tool schema + specialised prompt + serialised context
  - Result passing: tool results must be serialised back to supervisor
  Estimated cost increase: 15-30% for simple single-tool queries, potentially
  cost-neutral or cheaper for complex multi-tool queries (due to smaller per-call
  context).

4.5 ORCHESTRATION COMPLEXITY (MEDIUM IMPACT)
  New infrastructure required:
  - Subagent lifecycle management (instantiation, timeout, cleanup)
  - Context serialisation/deserialisation between supervisor and subagents
  - Error propagation and retry logic at TWO levels (supervisor + subagent)
  - Async orchestration for parallel subagent execution
  - Result aggregation and formatting in the supervisor
  - Session memory management becomes harder (supervisor owns memory, subagents don't)
  Estimated development effort: significant refactoring of wazuh_agent.py, new
  subagent runner class, context serialisation layer.

4.6 SUPERVISOR STILL NEEDS TOOL KNOWLEDGE (MEDIUM IMPACT)
  The supervisor must understand enough about each tool to:
  - Route queries to the correct subagent(s)
  - Know when to invoke multiple subagents
  - Understand partial failures and decide on retries
  - Synthesise results from multiple subagents into coherent responses
  This means the supervisor's prompt still needs meaningful tool descriptions
  (even if shorter than the full schemas), reducing some of the token savings.

4.7 RESULT SYNTHESIS QUALITY (MEDIUM IMPACT)
  Currently, the single agent has full context when generating the final response:
  - It saw the raw tool outputs
  - It knows what it tried and why
  - It can cross-reference between tool results
  With multi-agent, the supervisor synthesises from serialised subagent outputs.
  The quality of the final response depends on how well the supervisor can
  interpret and correlate results it didn't directly generate.

================================================================================
5. SYNCHRONOUS VS ASYNCHRONOUS SUBAGENT INVOCATION
================================================================================

5.1 SYNCHRONOUS (SEQUENTIAL)
  Use when: Tool B depends on Tool A's output
  Example: "Investigate the host with the most alerts" requires:
    1. AnalyzeAlerts (find top host) -> result: "win-4"
    2. InvestigateEntity (investigate win-4) -> result: entity details
  This is the safer default and matches the current agent's sequential reasoning.

5.2 ASYNCHRONOUS (PARALLEL)
  Use when: Tools are independent
  Example: "Check vulnerabilities and monitor agent health for host X"
    1. CheckVulnerabilities(entity_filter="X") |  concurrent
    2. MonitorAgents(agent_id="X")             |
  Requires: async orchestration (asyncio.gather), timeout handling per subagent,
  result aggregation. LangChain supports async tool execution already.

5.3 RECOMMENDATION
  Support BOTH modes with the supervisor deciding based on query analysis.
  Default to synchronous for safety. Use async only for clearly independent queries.
  The supervisor's routing prompt should explicitly classify: "sequential" vs "parallel".

================================================================================
6. SHOULD SUBAGENTS USE THE SAME CLAUDE-SONNET MODEL?
================================================================================

6.1 ANALYSIS
  The current system uses claude-sonnet-4-20250514 for everything. For subagents:

  Tool                    | Reasoning Complexity | Recommended Model
  ------------------------|---------------------|--------------------------
  AnalyzeAlerts           | Low-Medium          | Haiku (cheaper, faster)
  InvestigateEntity       | Low                 | Haiku
  MapRelationships        | HIGH                | Sonnet (directional logic)
  DetectThreats           | Medium              | Haiku or Sonnet
  FindAnomalies           | Medium-High         | Sonnet (RCF interpretation)
  TraceTimeline           | Low-Medium          | Haiku
  CheckVulnerabilities    | Low                 | Haiku
  MonitorAgents           | Low                 | Haiku

  Supervisor              | HIGH                | Sonnet (routing + synthesis)

6.2 RECOMMENDATION
  Do NOT use the same model for all subagents. Differentiate by complexity:
  - Supervisor: claude-sonnet-4 (strong reasoning for routing and synthesis)
  - Complex subagents (MapRelationships, FindAnomalies): claude-sonnet-4
  - Simple subagents (MonitorAgents, CheckVulnerabilities, InvestigateEntity):
    claude-haiku (faster, ~10x cheaper, sufficient for parameter extraction)

  Estimated savings: 30-50% cost reduction on subagent calls while maintaining
  quality for complex tools. The supervisor remains the most expensive component.

  CAVEAT: Even "simple" tools occasionally require nuanced parameter extraction
  (e.g., detecting that "OneDrive.exe" should map to entity_type="process",
  entity_id="C:\Users\...\OneDrive.exe"). Test Haiku thoroughly on real queries
  before deploying; fall back to Sonnet if accuracy drops.

================================================================================
7. OVERALL RECOMMENDATION
================================================================================

7.1 VERDICT: THE MULTI-AGENT APPROACH IS PREMATURE FOR THIS APPLICATION

  The current single-agent architecture is well-suited to the THF's needs because:

  a) The application's primary value is MULTI-STEP ADAPTIVE REASONING
     The example workflow shows the agent autonomously trying alternative approaches
     when initial tool calls fail. This is the hardest capability to replicate in a
     multi-agent system, and it's the most valuable for threat hunting.

  b) 8 tools is within the manageable range for a single agent
     LLM agents typically degrade at 15-20+ tools. With 8 well-defined tools and
     clear Pydantic schemas, Claude Sonnet handles routing effectively.

  c) Context preservation is already complex and working
     The ConversationContextProcessor + _merge_context_filters() system handles
     contextual references ("these alerts", "same host"). Adding an agent boundary
     between the context system and the tools would create new failure modes.

  d) The latency and cost trade-offs don't favour multi-agent here
     Most queries invoke 1-3 tools. The overhead of supervisor/subagent communication
     adds latency without proportional benefit for this query volume.

7.2 RECOMMENDED ALTERNATIVE: OPTIMISE THE SINGLE-AGENT ARCHITECTURE

  Instead of a full multi-agent refactor, address the current pain points:

  OPTIMISATION 1: DYNAMIC TOOL LOADING (HIGH VALUE, MEDIUM EFFORT)
    Add a lightweight "tool selector" step before the main agent:
    - A small/fast model (or even rule-based classifier) analyses the user query
    - Selects 2-3 relevant tools instead of loading all 8
    - The main agent runs with only the relevant tool schemas
    - Reduces input tokens by 50-70% per call
    - Preserves the single-agent's adaptive reasoning capability

  OPTIMISATION 2: COMPRESS TOOL DESCRIPTIONS (HIGH VALUE, LOW EFFORT)
    The tool descriptions are extremely verbose. For example, MapRelationshipsTool's
    description is ~50 lines. This can be reduced to ~10 lines by:
    - Moving detailed usage patterns to the Pydantic field descriptions
    - Using a concise "when to use / when NOT to use" format
    - Keeping only the most discriminating routing information in the description

  OPTIMISATION 3: SPLIT THE SYSTEM PROMPT (MEDIUM VALUE, LOW EFFORT)
    Move the anomaly-specific formatting rules (lines 88-117) out of the main
    system prompt. Inject them as a "tool-specific instruction" only when the
    FindAnomalies tool is selected. This keeps the base system prompt focused.

  OPTIMISATION 4: STRUCTURED OUTPUT FOR TOOL ROUTING (MEDIUM VALUE, MEDIUM EFFORT)
    Replace the freeform Thought/Action/Observation loop with a structured first
    step where the LLM outputs a plan:
    { "tools_needed": ["analyze_alerts", "map_relationships"],
      "execution_order": "sequential",
      "reasoning": "Need to filter alerts first, then map relationships" }
    Then execute the plan. This is a lighter-weight version of the supervisor
    pattern without the full subagent overhead.

7.3 WHEN TO REVISIT MULTI-AGENT

  Consider migrating to multi-agent architecture IF:
  - Tool count grows beyond 12-15 (routing accuracy will degrade)
  - New tools require fundamentally different model capabilities (e.g., a code
    analysis tool that needs a code-specialised model)
  - Parallel execution becomes critical (e.g., real-time dashboards needing
    concurrent data from multiple tools)
  - Subagent-specific fine-tuning becomes available and valuable
  - The application evolves to support multiple concurrent users where isolating
    subagent state becomes a scaling requirement

     - anomaly_detector: threshold/behavioral/trend anomalies

     - vulnerability_checker: CVE and patch analysis
     - agent_monitor: Wazuh agent health and status
     Output a JSON plan, then I will execute it."

  8.2 SUBAGENT INVOCATION (LangChain pattern):
    Each subagent is a separate AgentExecutor with:
    - Its own ChatAnthropic instance (potentially different model)
    - A single tool in its tools list
    - A specialised system prompt
    - No memory (stateless)
    - max_iterations=5 (simpler tasks, fewer retries needed)

  8.3 CONTEXT PASSING:
    The supervisor serialises relevant context before each subagent call:
    { "conversation_context": {
        "previous_host": "win-4",
        "previous_time_range": "3h",

      },
